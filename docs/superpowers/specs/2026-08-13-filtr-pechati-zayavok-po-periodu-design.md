# Фильтр периода при печати заявок

## Контекст

В CRM АХЧ печать заявок (DOCX-шаблоны в ZIP) сейчас работает поштучно: пользователь отмечает чекбоксами нужные заявки и нажимает «🖨 Печать (N)». Для руководителя неудобно отмечать десятки заявок вручную, когда нужно распечатать все документы за период.

## Цель

Дать администратору и директору возможность выбрать период по дате создания и/или дате завершения заявки, отметить все попавшие под фильтр заявки одной кнопкой, при необходимости скорректировать выбор вручную и распечатать.

## Ролевая модель

- Функциональность доступна только `director` и `admin`.
- Подрядчики (`contractor`) и коменданты (`comendant`) не затрагиваются.

## Места применения

1. Страница «Заявки» — `frontend/src/pages/RequestsListPage.jsx`.
2. Вкладка «Заявки» на дашборде — `frontend/src/pages/DashboardPage.jsx`, компонент `RequestsDashboard`.

## Архитектура

### Backend

Расширить эндпоинт списка заявок:

```
GET /api/requests
```

Новые query-параметры:

| Параметр | Тип | Описание |
|----------|-----|----------|
| `created_from` | `YYYY-MM-DD` | Начало периода по дате создания |
| `created_to` | `YYYY-MM-DD` | Конец периода по дате создания |
| `completed_from` | `YYYY-MM-DD` | Начало периода по дате завершения |
| `completed_to` | `YYYY-MM-DD` | Конец периода по дате завершения |

Фильтрация реализуется по аналогии с существующими фильтрами по датам в проекте (`requests.py`, `works.py`, `reports.py`):

- `created_from` → `Request.created_at >= datetime.combine(date, time.min)`
- `created_to` → `Request.created_at <= datetime.combine(date, time.max)`
- `completed_from` → `Request.completed_at >= datetime.combine(date, time.min)`
- `completed_to` → `Request.completed_at <= datetime.combine(date, time.max)`

Если параметр не передан — огранение не применяется.

Эндпоинт печати остаётся без изменений:

```
POST /api/requests/print
Body: [id1, id2, ...]
```

### Frontend

В обоих местах добавляется одна и та же группа элементов:

1. Четыре поля ввода даты (`<input type="date">`):
   - «Создана с»
   - «Создана по»
   - «Завершена с»
   - «Завершена по»
2. Кнопка «Выбрать все по фильтру»:
   - При нажатии `selectedIds` заполняется ID всех заявок, отображённых в текущем списке.
   - Если все уже выбраны — кнопка снимает выбор (toggle).
3. Существующая кнопка «🖨 Печать (N)» отправляет `selectedIds` на `POST /api/requests/print`.

При изменении любого фильтра (статус, корпус, даты) список перезагружается через `requestsAPI.list(params)`, а `selectedIds` сбрасывается, чтобы случайно не попали заявки, не соответствующие новому фильтру.

## Поток данных

1. Пользователь открывает страницу заявок.
2. Устанавливает статус/корпус и диапазоны дат.
3. Frontend вызывает `requestsAPI.list({ status, building_id, created_from, created_to, completed_from, completed_to })`.
4. Backend возвращает отфильтрованный список.
5. Пользователь нажимает «Выбрать все по фильтру» — все отображённые ID попадают в `selectedIds`.
6. При необходимости пользователь снимает/добавляет отдельные чекбоксы.
7. Пользователь нажимает «🖨 Печать (N)» — frontend отправляет `POST /api/requests/print` с итоговым массивом ID.
8. Backend формирует ZIP с DOCX, как сейчас.

## Обработка ошибок

- Некорректный формат даты: backend возвращает 422 (Pydantic/FastAPI по умолчанию), frontend показывает alert.
- Нет заявок по фильтру: показывается сообщение «Заявки не найдены».
- Ошибка печати: существующий alert с `e.response?.data?.detail`.

## Тестирование

- Backend: тест на `GET /api/requests` с фильтрами `created_from`, `created_to`, `completed_from`, `completed_to`.
- Backend: тест на комбинацию фильтров (статус + даты).
- Frontend: ручная проверка выбора по фильтру и печати на странице `/requests` и во вкладке дашборда.

## Не входит в задачу

- Изменение формата DOCX-шаблона заявки.
- Добавление фильтров для печати актов сдачи-приёмки (`/api/reports/act`) — там фильтр по периоду уже реализован.
- Автоматическая печать без промежуточного выбора чекбоксов (вариант B отклонён).
