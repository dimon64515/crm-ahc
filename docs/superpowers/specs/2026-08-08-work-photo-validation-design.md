# Дизайн: проверка фотографий в отчётах подрядчиков

## Контекст

Подрядчики прикрепляют фото к отчётам о проделанной работе (`Work` → `WorkPhoto`).
Сейчас система не извлекает и не проверяет EXIF-метаданные фотографий. Нужно
добавить контроль за датой съёмки и наличием геопозиции, а также ввести
этап ручной проверки администратором для "проблемных" отчётов.

## Цели

1. Извлекать из фото дату съёмки (`DateTimeOriginal`) и GPS-координаты.
2. Проверять, что фото сняты в корректном временном окне относительно заявки.
3. Проверять, что у фото есть геопозиция.
4. Не позволять формировать акты и печатные формы по непроверенным/отклонённым отчётам.
5. Дать администратору интерфейс для утверждения или отклонения отчётов.

## Out of scope

- Наложение даты/времени на само изображение (оверлей).
- Проверка фото заявок (`RequestPhoto`).
- Фоновая обработка через очереди (Celery/RQ).
- Сравнение GPS с координатами корпуса — только факт наличия координат.

## Бизнес-правила

### Создание отчёта

- Отчёт о работе (`Work`) обязательно должен содержать хотя бы одно фото.
- Работа создаётся только на основании заявки (`request_id` обязателен).
  > Примечание: в текущей модели `Work.request_id` технически `nullable`.
  > Это отдельная задача на приведение кода и документации к реальной бизнес-логике.

### Проверка каждого фото

Фото считается валидным, если:

1. В EXIF присутствует `DateTimeOriginal`.
2. В EXIF присутствуют GPS-координаты (широта и долгота).
3. Дата съёмки удовлетворяет условию:
   - `photo_taken_at.date >= request.created_at.date`
   - `photo_taken_at.date <= request.created_at.date + 3 дня`

### Проверка отчёта

Отчёт считается валидным, если:

- В отчёте есть хотя бы одно фото.
- Все фото отчёта валидны.

### Статусы работы

- `pending` — отчёт создан и ожидает проверки/утверждения администратором.
- `approved` — отчёт проверен и принят.
- `rejected` — отчёт отклонён администратором.

Правила переходов:

- После создания работы и загрузки фото статус устанавливается автоматически:
  - `approved`, если отчёт валиден.
  - `pending`, если есть проблемы с фото.
- Администратор может перевести `pending` → `approved` или `pending` → `rejected`.
- Администратор может перевести `approved` → `rejected`.
- Перевод `rejected` обратно не предусмотрен; подрядчик создаёт новый отчёт.

### Связь с заявкой

- При успешном создании отчёта заявка переходит в `completed` (как сейчас).
- При отклонении отчёта (`pending` → `rejected` или `approved` → `rejected`):
  - Связанная заявка возвращается в статус `new`.
  - Поле `assigned_to` заявки очищается, чтобы заявка снова стала доступна
    любому подрядчику.

### Акты и отчёты

- Экспорт Excel (`/reports/export`) и генерация акта (`/reports/act`)
  включают только работы со статусом `approved`.
- Сводный отчёт (`/reports/summary`) также учитывает только `approved` работы.

## Архитектура

### Изменения в моделях

#### `WorkPhoto`

```text
photo_taken_at   DateTime  nullable
latitude         DECIMAL(10, 8)  nullable
longitude        DECIMAL(11, 8)  nullable
has_exif_date    Boolean   default=False
has_gps          Boolean   default=False
is_valid         Boolean   default=False
```

#### `Work`

```text
status               String(20)   default='pending'
validation_checked_at DateTime  nullable
approved_by          Integer (FK → users.id)  nullable
approved_at          DateTime  nullable
rejected_by          Integer (FK → users.id)  nullable
rejected_at          DateTime  nullable
rejection_reason     Text      nullable
```

### Сервисы

#### `backend/app/services/photo_metadata_service.py` (новый)

- `extract_metadata(image_bytes: bytes) -> PhotoMetadata`
  - Извлекает `DateTimeOriginal` и GPSInfo через Pillow.
  - Конвертирует GPS в десятичные градусы.
  - Возвращает датакласс/словарь с полями `photo_taken_at`, `latitude`,
    `longitude`, `has_exif_date`, `has_gps`.

#### `backend/app/services/photo_validation_service.py` (новый)

- `validate_work_photos(work: Work) -> ValidationResult`
  - Проверяет все фото работы по бизнес-правилам.
  - Возвращает результат и список ошибок по каждому фото.
  - Формат ошибок: список объектов `{photo_id, filename, errors: ["нет даты", "нет геопозиции", "дата вне диапазона"]}`.
- `recalculate_work_status(work: Work) -> str`
  - Устанавливает `Work.status` в `approved` или `pending`.
  - Обновляет `validation_checked_at`.

### Изменения в существующих сервисах

#### `backend/app/services/file_service.py`

- `save_photo(...)` вызывает `extract_metadata(...)` и возвращает
  метаданные вместе с текущими полями.

### API

#### Изменённые эндпоинты

- `GET /works`
  - Добавлен query-параметр `status`.
  - В ответе каждого элемента добавлены `status` и краткая информация
    о валидации.
- `GET /works/{work_id}`
  - В ответ добавлены `status`, `validation_errors`, `approved_at`,
    `rejected_at`, `rejection_reason`.
  - Для каждого фото добавлены `photo_taken_at`, `latitude`, `longitude`,
    `has_exif_date`, `has_gps`, `is_valid`.
- `POST /works`
  - Создаёт работу со статусом `pending`.
  - Фото не передаются в этом запросе (двухэтапная схема сохранена).
  - Фронтенд не позволяет нажать "Сохранить", пока не выбрано хотя бы одно фото.
- `POST /works/{work_id}/photos`
  - Если список файлов пустой, возвращается ошибка 400.
  - После сохранения всех фото вызывает `recalculate_work_status`.
  - В ответ добавляет `work.status` и `validation_errors`.

#### Новые эндпоинты

- `POST /works/{work_id}/approve`
  - Только `admin`.
  - Статус работы → `approved`.
  - Записывает `approved_by`, `approved_at`.
- `POST /works/{work_id}/reject`
  - Только `admin`.
  - Принимает JSON `{"reason": "..."}`.
  - Статус работы → `rejected`.
  - Записывает `rejected_by`, `rejected_at`, `rejection_reason`.
  - Связанная заявка возвращается в статус `new`.

#### Отчёты

- `/reports/export`, `/reports/act`, `/reports/summary` фильтруют
  работы по `status == 'approved'`.

### Фронтенд

#### `WorkFormPage.jsx`

- Кнопка "Сохранить" неактивна, пока не выбрано хотя бы одно фото.
- После сохранения отображается итоговый статус:
  - "Отчёт принят" (`approved`).
  - "Отчёт отправлен на проверку: у фото отсутствуют дата/геопозиция"
    (`pending`).

#### `DashboardPage.jsx`

- Новая секция "Отчёты на проверке" для `admin`/`director`.
- Таблица работ со статусами `pending` и `rejected`.
- Колонки: подрядчик, корпус, дата работы, заявка, список ошибок.
- Для `admin` — кнопки "Утвердить" и "Отклонить" (с полем причины).

#### `WorkDetailPage.jsx`

- Отображение статуса работы.
- Для каждого фото — дата съёмки, координаты, иконки/тексты предупреждений
  при отсутствии данных.
- Для `admin` — блок управления статусом: approve/reject + reason.

#### `MyWorksPage.jsx`

- В списке и карточке подрядчика отображается статус работы.
- Отклонённые работы помечаются явно.

## Миграции

1. Добавить поля в `work_photos`.
2. Добавить поля в `works`.
3. Существующим работам проставить `status = 'approved'`.
4. Существующие фото оставить с `NULL` метаданными.

## Безопасность и права

- Утверждать/отклонять работы может только `admin`.
- Просматривать список на проверке могут `admin` и `director`.
- Подрядчик видит только свои работы и их статусы.

## Ошибки и крайние случаи

- Фото без EXIF-данных: отчёт получает `pending`, ошибка указывает
  на конкретное фото.
- Дата съёмки раньше даты заявки или позже +3 дней: отчёт `pending`.
- Фото без GPS: отчёт `pending`.
- Отчёт без фото: запрещено создавать на фронтенде; на backend — 400.
- Невалидный формат даты в EXIF: обрабатывается как отсутствие даты.
- Некорректные GPS-данные: обрабатываются как отсутствие GPS.

## Метрики и мониторинг

- В dashboard видно количество отчётов `pending` и `rejected`.
- В деталях работы видны конкретные причины блокировки.
